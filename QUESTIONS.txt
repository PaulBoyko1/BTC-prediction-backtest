BASELINE DECISIONS ALREADY ANSWERED
===================================

YOUR ANSWER (NORMALIZED)
------------------------
You want a highly configurable research/backtest system rather than one hard-coded strategy. The system should be able to test prediction-market ideas, BTC ideas, and combinations of both; use realistic execution assumptions; compare Kalshi and Polymarket independently; expose differences rather than hiding them; and preserve enough raw data/timing detail to investigate whether an apparent edge is real.

This translates into the following already-approved requirements:

- Always show separate 1-year, 2-year and 3-year requested windows when real history actually exists.
- Never fake a full requested window by padding missing prediction-market history with synthetic data.
- Show Kalshi and Polymarket separately, plus a venue-equity difference visualization.
- Use executable ask as the default buy assumption.
- Automatically run last-trade and midpoint sensitivity variants as well.
- Prominently flag unusually large ask-vs-last/midpoint result differences.
- Make re-entry behavior configurable.
- Support hold-to-expiry, price target, target+stop and time-before-expiry exits.
- Support defined-price cycles such as buy <=45c / sell >=55c.
- Support repeated low->high cycles inside one contract when re-entry is enabled.
- Allow BTC, prediction-market and settlement-reference factors to be mixed in the same strategy.
- Starting from the BTC or Prediction branch must not lock the user into only that factor family.
- VWAP needs named bullish/bearish/reversal/continuation/support/resistance/breakthrough behavior plus customization.
- Test B — prediction market moves sharply while BTC itself barely moved — is a first-class research idea.
- BTC source defaults to an explicit Binance + Coinbase composite and can also be studied by source separately.
- Kalshi and Polymarket settlement references must remain separate from exchange spot.
- Preserve native/raw timestamps before optional aggregation.
- Risk/sizing assumptions are configurable research controls, not fixed recommendations.
- Advanced statistics need plain-English explanations.
- Parameter sweeps are required, but a best historical parameter is not automatically an edge.
- Cross-venue discrepancy analysis stays separate from ordinary strategy testing.
- Tests A, B, C and E all belong in the system:
  A = contract-price threshold / price-cycle ideas.
  B = prediction-market shock while BTC barely moved, then measure BTC response.
  C = Kalshi <-> Polymarket discrepancy / confirmation.
  E = BTC technical conditions mapped into prediction-market trades.
- No automatic real-money order placement is part of the research system.

The v0.5 regression suite now explicitly tests the 45c->55c mean-reversion case and repeated volatility-harvesting cycles, including the important case where an early exit makes money even though the contract ultimately settles against the purchased side. See LOGIC_AUDIT.md.

5. HISTORICAL FEE SCHEDULES
---------------------------
STATUS: RESOLVED PRINCIPLE

YOUR ANSWER (NORMALIZED):
Yes. A strategy should be judged after real fees, spread, slippage and other execution costs. If a venue changed its fees, the historical backtest should use the fee structure that actually applied at that time instead of one modern fixed estimate.

WHY THIS IS NOW MANDATORY, NOT OPTIONAL:
- Kalshi states that fees can differ across markets and that some markets have maker fees.
- Polymarket now has fee-enabled market categories, market-level feesEnabled state and activation timing. Current crypto taker fees use a nonlinear probability-dependent formula rather than a constant cents/share assumption.

CURRENT POLYMARKET FORMULA (verified 2026-08-23):
fee = shares * feeRate * p * (1 - p)
Current Help Center lists crypto taker feeRate = 0.07, maker fee = 0, with fee applicability determined by the market/category/deployment regime. Those values can change, so they must be captured from the market/fee regime rather than hard-coded forever.

REPO MEANING:
Production normalized contracts/trades should store fee-regime/version metadata. The current fixed entryFeeCents/exitFeeCents browser controls remain sensitivity allowances only.

VERIFIED SOURCES:
- https://help.kalshi.com/en/articles/13823805-fees
- https://help.polymarket.com/en/articles/13364478-trading-fees
- https://help.polymarket.com/en/articles/13364471-maker-rebates-program


6. MAKER MODEL
--------------
STATUS: PARTIALLY RESOLVED

YOUR ANSWER (NORMALIZED):
Do not spend the first stage building a complicated maker simulation. First find ideas that survive conservative executable/taker assumptions. If an idea survives, then investigate whether maker execution improves it realistically.

WHAT YOU HAVE NOT YET EXPLICITLY CHOSEN:
You have not selected one exact maker-fill algorithm.

REPO-SPECIFIC RECOMMENDATION:
When this is built, do NOT use "limit touched = filled" as the serious result. That is too optimistic for high-frequency work. Prefer a queue/depth/order-flow model that can represent:
- queue position;
- displayed depth ahead;
- partial fills;
- order cancellation/replacement;
- adverse selection after fill;
- maker fees/rebates by venue/regime.

WHY:
A prediction market can touch a price without enough opposing flow to fill our order. Treating every touch as a fill creates artificial edge.

VERIFIED STATE:
The repo intentionally has no realistic maker result yet. v0.5 still treats taker/ask execution as the credible first-stage assumption.
